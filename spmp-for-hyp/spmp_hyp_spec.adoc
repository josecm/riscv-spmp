== Specification

=== Hypervisor-Extended SPMP (hSPMP)

The Shpmp extension augments the baseline SPMP functionality to support virtualization through integration with the RISC-V Hypervisor extension. When the Hypervisor extension is present, SPMP behavior is extended to form hypervisor-extended SPMP (hSPMP). When V = 0, hSPMP behaves identically to the baseline SPMP. When V = 1 and hgatp.MODE = Bare, hSPMP enforces access checks on all memory accesses from VS-mode and VU-mode, effectively applying SPMP protections to guest execution contexts. The permission encodings remain consistent with those of the baseline SPMP when spmpcfg.S = 0, but are applied to VS/VU modes rather than U-mode. Additionally, the Hypervisor Virtual Machine Load and Store instructions (HLV, HLVX, HSV), when executed from M-mode, HS-mode, or HU-mode (when hstatus.HU = 1), are also subject to hSPMP checks under the V = 1 condition.

When a guest access is denied by hSPMP, an exception is raised. The type of exception depends on the nature of the access attempt, i.e., whether it is a load, store/AMO, or instruction fetch. The hSPMP reuses the guest page fault exception codes defined by the Hypervisor extension, since SPMP and paged virtual memory are mutually exclusive; SPMP is only active when satp.MODE = Bare. Consequently, paged virtual memory-based translations are disabled, and the guest page fault exception codes are repurposed to indicate guest SPMP access violations.

The hSPMP extension introduces an additional WARL indirect access register pair, hspmpswitch0–hspmpswitch1, to complement the baseline SPMP. When V = 1, these registers replace the function of spmpswitch0–spmpswitch1. Specifically, under V = 1, an hSPMP entry is considered active only if both the corresponding bit in hspmpswitch is set and the A (Active) bit in the associated spmp[i]cfg register is set. When V = 0, the hspmpswitch registers have no effect, and the baseline SPMP behavior applies as defined by spmpswitch alone.

=== Guest/Virtual SPMP (vSPMP)

This extension introduces a new memory protection layer called Virtual SPMP (vSPMP). The vSPMP behaves analogously to the baseline SPMP but is under the control of VS-mode and applies to memory accesses originating from VS and VU modes. The vSPMP is active only when V = 1. Conceptually, this extension establishes a two-stage SPMP hierarchy, preceding any checks by PMP or ePMP (see <<hpmp-arch>>). From a logical perspective, when both vsatp.MODE and hgatp.MODE are set to Bare, memory accesses initiated by guest contexts (VS/VU) are subject to the following enforcement sequence: 

    1. vSPMP check: If the access is permitted by vSPMP, then 
    2. hSPMP check: The access must also be permitted by hSPMP. 

If the vSPMP check or both the vSPMP and hSPMP checks deny a VS/VU access, a standard SPMP page-fault direct at VS-mode is triggered using exception codes  12 (instruction), 13 (load), or 25 (store/AMO), in alignment with standard fault code semantics. If only the hSPMP denies a VS/VU access, a guest page-fault directed at HS-mode is raised using exception codes 20 (instruction), 21 (load), or 23 (store/AMO). Implementations may perform vSPMP and hSPMP checks in parallel, provided the overall enforcement behavior matches the sequential logic described above.

For consistency with the baseline Hypervisor specification, and from a logical perspective, addresses evaluated by the vSPMP are considered Guest Virtual Addresses (GVA), while those evaluated by the hSPMP are considered Guest Physical Addresses (GPA).

When vsatp.MODE is set to Bare but hgatp.MODE is not, the vSPMP check is logically followed by G-stage address translation. Implementations may perform the vSPMP check and G-stage translation in parallel.

When vsatp.MODE is not set to Bare, but hgatp.MODE is, the hSPMP check logically occurs after the VS-stage address translation. In this scenario, the Guest Physical Address (GPA) produced by the VS-stage translation must be used as the input to the hSPMP check. Consequently, parallel evaluation of VS-stage translation and hSPMP enforcement is not possible unless speculative techniques are employed.

VS-mode configures the vSPMP through a set of Virtual Supervisor (VS) indirect-access registers, which are architectural replicas of the standard SPMP supervisor indirect-access registers. These include vspmpcfg0–vspmpcfg3, vspmpaddr0–vspmpaddr63, and vspmpswitch0–vspmpswitch1. Consistent with the behavior defined in the baseline Hypervisor specification, when V = 1, accesses to the original SPMP registers from VS-mode are transparently redirected to the corresponding vSPMP registers.

The number of supported vSPMP entries is implementation-defined. However, the architecture permits support for up to 64 entries, consistent with the maximum defined for standard SPMP.

=== Resource Sharing

In analogous way to how M-mode can delegate entries from the global PMP_Resource resource pool to the SPMP, hypervisor can delegate entries to the vSPMP. For this we introduce a new `hpmpdeleg` CSR with the same format and functionality of `mpmpdeleg`. Any PMP_Resource greater than or equal to the `mpmpdeleg.pmpnum` + `hpmpdeleg.pmpnum` is delegated to the vSPMP.
